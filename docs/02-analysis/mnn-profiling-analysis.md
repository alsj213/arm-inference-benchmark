# MNN MobileNetV2 Profiling 分析报告

**测试日期**：2026-04-27
**设备**：Redmi K30 Pro (Snapdragon 865)
**模型**：MobileNetV2 (fp32, 1x3x224x224)
**工具**：simpleperf --call-graph dwarf

---

## 1. 核心发现：线程同步是主要瓶颈

通过火焰图分析发现，MNN 推理在 4 线程配置下，**49% 的 CPU 时间花在内核调度器（`sched_yield`）**，而不是真正的计算。

```
4 线程采样分布：
├── 49.4%  内核调度器 (sched_yield)    ← 瓶颈！线程在空转等待
├── 26.0%  LoopL2 (矩阵乘法)          ← 真正的计算
├──  3.9%  LoopE12L4 (卷积)
├──  2.9%  sched_yield (用户态)
├──  2.6%  L16LoopW (Winograd变换)
├──  1.8%  E1LoopL
└── ~13%   其他 (memcpy, libc等)
```

### 调用链分析

所有 49% 的内核采样都来自同一条调用链：

```
__start_thread
  → __pthread_start
    → MNN::ThreadPool::ThreadPool()::$_0    (工作线程入口)
      → sched_yield                         (让出 CPU)
        → 内核调度器                        (上下文切换)
```

这是 MNN 线程池的**工作线程在调用 `sched_yield` 让出 CPU**，说明线程池里没有足够的任务给所有线程执行。

## 3. 原因分析

### 为什么 4 线程比 2 线程慢？

MobileNetV2 是轻量级模型，每个推理的计算量不大（~2.3 GFLOPs）。4 个线程分到的任务太少，工作线程频繁调用 `sched_yield` 等待新任务。

每次 `sched_yield` 的开销：
- 触发内核上下文切换：~1-10μs
- 4 线程时，每秒约 80,000+ 次 yield
- 累计开销超过多核并行带来的收益

### MNN 线程池的工作模式

```
主线程:  提交任务 → 等待完成
工作线程: 取任务 → 执行 → 无任务时 sched_yield → 取任务 → ...
```

当任务粒度太细或任务数不够时，工作线程大部分时间在 yield，而不是计算。

## 5. 建议

### 对于 MobileNetV2

- **推荐线程数：2** — 最佳吞吐量 68 FPS
- 避免使用 4 线程，调度开销会抵消并行收益

### 对于更大模型

- 更大模型（ResNet50、BERT 等）计算量更大，4 线程可能更合适
- 需要实际测试确定最优线程数

### 通用建议

1. **不要盲目使用最大线程数** — 轻量级模型用少线程更快
2. **profile-driven optimization** — 先用火焰图分析瓶颈，再优化
3. **关注内核占比** — 如果内核占比 > 20%，说明线程同步开销过大
