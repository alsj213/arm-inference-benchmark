# 火焰图阅读指南 — 从入门到实战

---

## 1. 什么是火焰图？

火焰图（Flame Graph）是一种**可视化性能分析数据**的图表，用来回答一个问题：

> **程序把 CPU 时间花在了哪里？**

它不是"火焰"，更像是**一堆叠起来的积木**。每个积木是一个函数，积木越宽 = 这个函数（及其调用的子函数）占用的 CPU 时间越多。

---

## 2. 基本术语

| 术语 | 英文 | 含义 |
|------|------|------|
| **采样** | Sample | simpleperf 每隔一段时间（如 0.25ms）记录一次"CPU 正在执行哪个函数"，每一次记录就是一个采样 |
| **调用栈** | Call Stack / Call Chain | 函数 A 调用函数 B，B 调用 C，形成 A → B → C 的调用链 |
| **叶子函数** | Leaf Function | 调用栈最顶部的函数，**真正占用 CPU 的函数** |
| **帧** | Frame | 火焰图中的一个小方块，代表一个函数 |
| **深度** | Depth | 调用栈的层数，从底部到顶部的帧数 |
| **开销** | Overhead / Self | 某个函数自身执行代码的时间（不算它调用的子函数） |
| **累计开销** | Children / Cumulative | 某个函数 + 它调用的所有子函数的总时间 |
| **DSO** | Dynamic Shared Object | 动态链接库，如 `libMNN.so`、`libc.so` |
| **符号** | Symbol | 函数名（如 `LoopL2`、`memcpy`） |
| **折叠格式** | Folded Format | 一种文本格式，每行表示一个完整调用栈，如 `main;infer;LoopL2 1` |

---

## 3. 火焰图的坐标轴

```
Y 轴（垂直方向）
│
│  ┌─────────┐  ← 叶子函数（最顶部，真正消耗CPU的函数）
│  │  LoopL2  │
│  ├─────────┤
│  │  infer   │  ← 中间层（调用链）
│  ├─────────┤
│  │   main   │  ← 根函数（最底部，程序入口）
│  └─────────┘
└────────────────── X 轴（水平方向）
```

- **Y 轴（垂直）**：调用栈深度。底部是 `main`，顶部是当前正在执行的函数
- **X 载（水平）**：采样数量。方块越宽 = 这个函数出现的次数越多 = 花的 CPU 时间越多
- **颜色**：随机分配，**没有特殊含义**（不要被颜色迷惑）

---

## 4. 核心阅读技巧

### 技巧一：先看最宽的方块

最宽的方块 = CPU 时间占比最大的函数。这是你应该**优先优化**的地方。

```
窄的（不重要）          宽的（重要！）
┌──┐                ┌──────────────────────────┐
│f │                │         LoopL2            │
└──┘                └──────────────────────────┘
 1%                          26%
```

### 技巧二：区分"自身开销"和"累计开销"

```
┌─────────────────────────────────────────┐
│              main (100%)                 │  ← 累计开销 100%
├─────────────────────────────────────────┤
│              infer (80%)                 │  ← 累计开销 80%
├──────────────────┬──────────────────────┤
│    LoopL2 (60%)  │    memcpy (10%)      │  ← LoopL2 自身 60%, memcpy 自身 10%
└──────────────────┴──────────────────────┘
```

- `main` 的累计开销是 100%（因为它调用了所有其他函数）
- `LoopL2` 的自身开销是 60%（它没有调用其他函数，60% 全是自己在执行）
- `memcpy` 的自身开销是 10%

**优化原则**：优先优化**自身开销大**的叶子函数，而不是累计开销大的父函数。

### 技巧三：看"塔"而不是"单个方块"

一个完整的调用栈像一座塔：

```
┌─────────────────┐
│    LoopL2       │  ← 叶子函数：真正消耗CPU
├─────────────────┤
│  lambda(int&&)  │  ← 调用者：触发了 LoopL2
├─────────────────┤
│ ThreadPool::    │  ← 线程池：分配了任务
│ enqueueInternal │
├─────────────────┤
│ Pipeline::      │  ← 执行管线：组织推理流程
│ execute         │
├─────────────────┤
│   runSession    │  ← 会话运行：MNN 推理入口
├─────────────────┤
│   infer         │  ← 后端推理调用
├─────────────────┤
│     main        │  ← 程序入口
└─────────────────┘
```

**阅读方法**：从下往上看 = 函数调用顺序；从上往下看 = 函数返回顺序。

### 技巧四：识别"宽底座"

如果底部的函数特别宽，说明程序大部分时间都在这个函数的调用链中：

```
┌──────────────────────────────────────────────┐
│                   main (100%)                 │  ← 宽底座：正常
└──────────────────────────────────────────────┘

┌──────────┐
│  main    │  ← 窄底座：可能有问题，大量时间不在 main 的调用链中
└──────────┘
┌──────────────────────────────────────────────┐
│              kernel (49%)                     │  ← 宽的其他底座：异常！
└──────────────────────────────────────────────┘
```

### 技巧五：关注"平顶"

如果某个函数的顶部是平的（没有子函数），说明这个函数**自身在做计算**，没有调用其他函数：

```
┌──────────────────────────────────────┐
│           LoopL2 (平顶)               │  ← 自身计算，没有子函数
├──────────────────────────────────────┤
│           调用者                       │
└──────────────────────────────────────┘
```

平顶函数是**优化的黄金目标** — 任何优化都能直接减少 CPU 时间。

## 5. 常见模式识别

### 模式一：计算密集型（健康）

```
┌──────────────────────────────────────────┐
│  LoopL2 (66%)     LoopE12L4 (10%)        │  ← 大部分时间在计算
├──────────────────────────────────────────┤
│           调用链                           │
└──────────────────────────────────────────┘
```

**特征**：叶子函数占比高，说明 CPU 在做有用的工作。

### 模式二：调度开销大（不健康）

```
┌──────────────────────────────────────┐
│  kernel/sched_yield (49%)             │  ← 大量时间在内核调度
├──────────────────────────────────────┤
│  MNN::ThreadPool (54%)               │
├──────────────────────────────────────┤
│           main                        │
└──────────────────────────────────────┘
```

**特征**：内核函数占比高，说明线程在频繁切换/等待。

### 模式三：内存瓶颈

```
┌──────────────────────────────────────┐
│  memcpy (30%)     memset (15%)        │  ← 大量时间在内存操作
├──────────────────────────────────────┤
│           调用链                       │
└──────────────────────────────────────┘
```

**特征**：`memcpy`、`memset`、内存分配函数占比高。

### 模式四：锁竞争

```
┌──────────────────────────────────────┐
│  futex_wait (40%)                     │  ← 大量时间在等待锁
├──────────────────────────────────────┤
│  pthread_mutex_lock                   │
├──────────────────────────────────────┤
│           调用链                       │
└──────────────────────────────────────┘
```

**特征**：`futex`、`pthread_mutex`、`lock` 相关函数占比高。

## 6. SpeedScope 使用技巧

SpeedScope (https://www.speedscope.app) 是在线火焰图查看器。

### 打开方式

1. 打开 https://www.speedscope.app
2. 把 `out.folded` 文件拖进去

### 三种视图模式

| 模式 | 快捷键 | 说明 |
|------|--------|------|
| **火焰图** | `1` | 经典火焰图，从下到上阅读 |
| **火焰列表** | `2` | 按自身开销排序的列表，快速找到最耗时的函数 |
| **三明治** | `3` | 同时看调用者和被调用者，适合分析调用关系 |

### 常用快捷键

| 快捷键 | 功能 |
|--------|------|
| `W` / `S` | 放大 / 缩小 |
| `A` / `D` | 左移 / 右移 |
| `方向键` | 平移视图 |
| `点击方块` | 聚焦到该函数 |
| `右键方块` | 复制函数名 |

### 实用技巧

1. **用火焰列表模式找热点**：按 `2` 切换到列表模式，按 Self 时间排序，第一个就是最大的性能瓶颈
2. **用搜索功能**：按 `/` 搜索函数名，快速定位特定函数
3. **点击方块看详情**：点击后会显示该函数的调用者（谁调用了我）和被调用者（我调用了谁）

## 7. 实战分析流程

### Step 1：看 DSO 分布

先看哪些 `.so` 文件占用了最多时间：

```
benchmark_inference  42.64%   ← 你的代码 + MNN
kernel.kallsyms      51.91%   ← 内核（异常高！）
libc.so               5.45%   ← C 标准库
```

**判断**：内核占比 > 20% 通常意味着调度/IO 问题。

### Step 2：看 Top 5 热点函数

```
1. kernel/sched_yield   49.41%   ← 线程同步开销
2. LoopL2               26.00%   ← 矩阵乘法
3. LoopE12L4             3.93%   ← 卷积
4. sched_yield           2.92%   ← 用户态 yield
5. L16LoopW              2.56%   ← Winograd变换
```

**判断**：如果 Top 1 是内核函数，说明瓶颈不在计算，而在系统层面。

### Step 3：在火焰图中找调用链

看 Top 热点函数的调用链，理解它为什么被调用：

```
main → infer → runSession → Pipeline::execute → ThreadPool → sched_yield → kernel
```

**判断**：调用链是否合理？是否有不必要的调用？

### Step 4：对比不同配置

用不同参数（线程数、模型等）跑多次，对比火焰图：

```
1线程: LoopL2 66% (无调度开销)
4线程: LoopL2 26% (49% 调度开销)  ← 4线程反而更慢
```

### Step 5：得出结论并验证

```
结论：MobileNetV2 用 2 线程最优 (68 FPS)
验证：减少线程后重新 profile，确认调度开销下降
```

## 8. 术语速查表

| 缩写/术语 | 全称 | 含义 |
|-----------|------|------|
| `self` | Self Time | 函数自身执行时间（不含子函数） |
| `children` | Children Time | 子函数的执行时间 |
| `total` | Total Time | self + children |
| `inclusive` | Inclusive Time | = children，包含子函数的时间 |
| `exclusive` | Exclusive Time | = self，不包含子函数的时间 |
| `flat` | Flat Profile | 按 self 时间排序的函数列表 |
| `callgraph` | Call Graph | 函数调用关系图 |
| `folded` | Folded Format | `func1;func2;func3 count` 格式 |
| `DSO` | Dynamic Shared Object | 动态链接库 (.so) |
| `symbol` | Symbol | 函数名 |
| `sample` | Sample | 一次采样记录 |
| `event` | Event | 采样事件类型（cpu-cycles, cache-misses 等） |
| `overhead` | Overhead | 占比百分比 |
| `fp` | Frame Pointer | 帧指针（调用栈展开方式） |
| `DWARF` | Debug With Arbitrary Record Format | 调试信息格式（调用栈展开方式） |

## 9. 常见误区

### 误区一：颜色代表重要性

**错**。颜色是随机分配的，没有特殊含义。不要因为某个函数是红色就认为它更重要。

### 误区二：最宽的方块一定需要优化

**不一定**。如果最宽的方块是 `memcpy`，可能是算法设计问题（太多内存拷贝），而不是 `memcpy` 本身需要优化。

### 误区三：火焰图告诉你"为什么慢"

**不完全**。火焰图告诉你"时间花在哪里"，但不直接告诉你"为什么"。需要结合调用链和上下文分析。

### 误区四：看单个采样

**不要**。火焰图是统计结果，要看整体趋势，不要纠结单个采样。

### 误区五：忽略内核时间

**不要**。如果内核占比高（>20%），通常是调度、IO、锁竞争等问题，需要优先解决。

## 10. 一张图总结

```
                    ┌─────────────────────────────────────────┐
                    │            阅读火焰图的步骤              │
                    └─────────────────────────────────────────┘

    ① 看最宽的方块 → 找到 CPU 时间占比最大的函数
                    ↓
    ② 看它是叶子还是父函数 → 叶子=自身开销, 父=累计开销
                    ↓
    ③ 从下往上看调用链 → 理解为什么这个函数被调用
                    ↓
    ④ 识别异常模式 → 内核占比高? memcpy多? 锁竞争?
                    ↓
    ⑤ 对比不同配置 → 找到最优参数
                    ↓
    ⑥ 得出结论 → 告诉你应该优化什么
```
