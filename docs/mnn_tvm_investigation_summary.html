3. 调度开销：simpleperf 模块级实证

对 64²（小矩阵）和 4096²（大矩阵）做 CPU 周期采样：

模块 MNN 64² TVM 64² MNN 4096² TVM 4096²
框架计算 (.so) 34.4% 4.9% 97.8% 93.6%
调度 (benchmark) 0.8% 26.6% 1.6% 5.5%
libc (memcpy) 3.6% 40.4% 0.4% 0.9%
linker 59.6% 26.4% 0.2% 0.1%

根因：MNN 用 vtable 直接跳转（~3μs/次），TVM 用 PackedFunc 类型擦除（~32μs/次）。小矩阵时 TVM 的 26.6% CPU 消耗在类型检查/参数打包上，实际计算仅占 4.9%。

4. 纯计算效率：剥除调度后

用 4096² 的 simpleperf 数据剥除调度开销，只看纯 GEMM 算力：

总时间(ms) 计算占比 纯计算时间(ms) 纯计算 GFLOPS
MNN 2643.6 97.8% 2585 53.2
TVM 2282.1 93.6% 2135 64.4

同样的 Cortex-A77，TVM 生成的代码比 MNN 手写汇编多榨出 21% 算力。

5. 分块策略：固定 vs 自适应

MNN TVM
分块大小 固定 eP=12, hP=8 (96 元素) 自适应 (64→256 per dimension)
决定方式 编译时硬编码 LLVM 查询 -mcpu=cortex-a77 的 cache 参数
L1D 利用 ~384B (0.6%) ~32KB (50%)
2048² 的 micro-kernel 调用次数 ~43,690 ~64
A 元素复用次数 8 次 (micro-kernel 内) 128 次 (tile 内)
设计哲学 一次编译，处处运行 按目标 CPU 编译，极致性能

差距根因：MNN 的 12×8 分块是为 Cortex-A53（8 个 NEON 寄存器）的"最小公约数"设计的，无法利用 A77 的 32 个 NEON 寄存器和大 cache。TVM 按 -mcpu=cortex-a77 编译，LLVM 自动选择了适合 64KB L1 / 512KB L2 的分块大小。

6. Pack/Unpack 占比

用 1024²（pack < 1%）作为纯计算基准校准，反推各 shape：

Shape Pack 占比 结论
16² 81% 内存搬运远超计算
64² 22% 仍不可忽略
256² 9% 过渡区
≥1024² < 1% 计算完全主导

7. GPU 探索

MNN OpenCL 在 Adreno 650 + Android 12 上存在 SIGSEGV 兼容问题（MTE tagged pointer），未能完成 CPU/GPU 实测对比。onExecuteEnd 缺少 clFinish 同步的问题已定位并提交修复，但需配合设备端 MTE 禁用或换 ORT GPU 后端。

8. 一句话结论

MNN 胜在零开销调度（vtable 直调），TVM 胜在自适应编译优化（LLVM 感知 cache 参数）。交叉点在 ~500M FLOPs，大矩阵 TVM 纯计算快 21%。

选型速查

场景 推荐 理由
移动端 CV (MobileNet 等小模型) MNN 小算子多，低 overhead 碾压
大 GEMM / 大 Conv TVM 自适应分块释放额外 21% 算力
LLM Decode (单 token, M=1) MNN 延迟敏感，调度开销致命
LLM Prefill (大批次) TVM 大批次 GEMM，算力优先
